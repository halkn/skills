# Issue 本文の書式

実装計画を基本の型とし、不具合と検討は基本の型の一部の節を置き換える。

| 節 | 実装計画 | 小さな修正 | 不具合 | 検討 |
|----|----------|------------|--------|------|
| 目的 | 必須 | 必須 | 必須 | 必須 |
| 現状 | 必須 | 書かない | 事象 / 切り分け / 原因 に置き換え（必須） | 必須 |
| 決定事項 | 必須 | 書かない | 必須（直し方の方針） | 選択肢 に置き換え（必須） |
| Scope | 必須 | 必須（「含まない」は任意） | 必須 | 書かない |
| 完了条件 | 必須 | 必須 | 必須 | 判断基準 に置き換え（必須） |
| 実装時に決めること | 任意 | 書かない | 任意 | 書かない |
| 参照 | 任意 | 任意 | 任意 | 任意 |

「任意」の節は、書く中身があるときだけ書く。`<!-- -->` のコメントは書く内容の指示なので、本文には残さない。該当しない節は見出しごと削る。

## 基本の型（実装計画）

````markdown
## 目的

<!-- なぜやるか、終わったら何ができるようになるかを 2〜4 文で。
     実装者は、ここから判断の優先順位を読む -->

## 現状

<!-- 今どうなっていて、何が足りないか。
     - 現状の挙動は、ファイルパス（行番号）かコマンドとその出力で示す
     - 既にあって使えるもの（関数・フラグ・設計）と、足りないものを分けて書く
     - 試して取り下げた案・効かなかった対処があれば、何をしてなぜ駄目だったか -->

## 決定事項

<!-- 後から変わりやすい決定から順に並べる: データモデル → 型・公開インターフェース（CLI の引数、設定キー、出力形式、ファイル配置） → UX → その他。
     1 項目 = 決定 + 理由。採らない案は、実装者が選び直しそうなものだけ書く -->

- <決定>。理由: <なぜこれか>
- <採らない案>にしない。理由: <なぜ>

## Scope

**含む**

<!-- 満たすべき性質・できるようになることを並べる。どう実装するか（どのファイルをどの順で変えるか）は書かない -->

- <性質・機能>

**含まない**

<!-- やりたくなるが今回やらないこと。別 issue で扱うものは番号を添える -->

- <やらないこと>（#12）

## 完了条件

<!-- 全部満たしたら完了と判定できる条件。次を含める:
     - できるようになったこと（観測できる状態）
     - 壊していないこと（既存の挙動・テスト・安全性）
     - 通るべき検証コマンド
     - ドキュメントの更新が要るなら「<ファイル> の <節> に <内容> が書かれている」の形で。Scope には重ねて書かない -->

- <観測できる状態>
- `<検証コマンド>` が成功する

## 実装時に決めること

<!-- 実装者に任せる論点。選択肢、それぞれの帰結、推奨を書く。
     推奨を「安全側」で決めるときは、比べる 2 つの失敗（誤検知と見逃し、止まることと壊すこと）を名指しし、起きても害の小さい失敗を許す側を推奨にする。
     ユーザーが決めないと進めない論点はここに置かず、作成前に決めて「決定事項」に入れる -->

- <論点>: <選択肢 A> か <選択肢 B> か。<推奨とその理由>

## 参照

<!-- 着手前に読むもの（何の判断に使うか）と、関連 issue との関係 -->

- `docs/design.md` の <節> — <何の判断に使うか>
- #13 とは別の問題。#13 は <…>、これは <…>
````

## 小さな修正

基本の型から「目的」「Scope」「完了条件」だけを残す。目的は 1〜2 文。「含まない」は、実装中に手を出したくなるもの（再発防止の仕組み、周辺の整理）があるときは書き、無ければ省く。

決定事項が要る（別の案を採ると実装が変わる選択がある）なら、小さな修正ではなく実装計画にする。

## 不具合

基本の型の「現状」を、次の 3 節に置き換える。「決定事項」には直し方の方針を書く。症状を隠す回避策（リトライ・待ち時間の延長・エラーの握りつぶし）を採らない場合は、その理由も書く。

````markdown
## 事象

<!-- 何をすると何が起きるか。再現手順、頻度、環境（ツールの版・OS）、実害 -->

## 切り分け

<!-- 試したことと結果。原因の候補を絞った根拠 -->

- <試したこと> → <結果>

## 原因

<!-- 特定できていなければ「未特定」と書き、次に見るべきところを書く。
     その場合、完了条件には「原因を特定する」を含める -->
````

完了条件には、事象の再現手順で事象が起きないことを含める。再現環境がユーザーの手元にしか無いときは、実装者が実行できる代わりの条件（再現に使う入力ファイルなど）と、「ユーザーが確かめる」と明記した条件に分けて書く。

## 検討

成果物はコードではなく結論。基本の型の「決定事項」を「選択肢」に、「完了条件」を「判断基準」に置き換え、「Scope」と「実装時に決めること」は削る。結論が出たら、コメントに結論を書いて close し、実装は新しい issue に分ける（この運用は issue 本文には書かない）。

````markdown
## 選択肢

<!-- 見えている案と、それぞれの利点・欠点。現状維持（見送り）が妥当なら、それも選択肢に入れる。推奨があれば書く -->

- A: <案> — <利点> / <欠点>
- B: <案> — <利点> / <欠点>

## 判断基準

<!-- どれを選ぶかを何で決めるか。実測が要るなら、何をどう測るか -->
````

## 書式上の規則

- 見出しはこのファイルに書いた名前（「Scope」を含む）をそのまま使い、`##` から始める。節の名前と順序は種類が違っても変えない（置き換える節はその位置に置く）
- タスクリスト（`- [ ]`）は使わない。Scope と完了条件は性質を並べる節で、チェックボックスにすると実装手順の一覧に見えてしまう。複数の issue をまとめる親 issue で、子 issue を `- [ ] #12` と並べるときだけ使う
- ログ・エラー出力・コマンドの出力・外部から貼った文章は、コードブロックか `>` 引用に入れる。本文の指示と、資料として貼った文章を区別するため（[agent-readable.md](agent-readable.md) の「貼った資料と指示を分ける」）
