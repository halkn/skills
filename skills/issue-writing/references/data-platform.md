# データ基盤の作業で足す基準

Snowflake・dbt・Azure Data Factory などのデータパイプラインを変える issue に、[agent-readable.md](agent-readable.md) の基準に加えて当てる。データ基盤以外の issue には当てない。

## 完了条件はデータで判定できる形にする

「正しく取り込まれる」「変換が直る」ではなく、データで判定できる条件を書く。

- dbt test（`dbt test --select <model>` が成功する、追加した test 名）
- 件数・差分の比較（変更前後の行数、主キーの重複が 0 件、旧モデルとの差分クエリが 0 行）
- 鮮度（最終ロード時刻が <基準> 以内）

比較に使うクエリや基準値が決まっているなら本文に書く。決まっていなければ「実装時に決めること」に、何と何を比べるかの推奨と一緒に置く。

- 理由: データの変更はコードのテストが通っても結果が正しいとは限らない。データで判定する条件が無いと、実装者はビルドの成功を完了とみなす

## 不可逆な操作は停止条件とロールバックを書く

DROP・TRUNCATE・上書きのバックフィル・本番データの変更・スキーマの破壊的変更（列の削除・型の変更・名前の変更）を含むなら、次を書く。

- 「停止条件」に、その操作を実行する手前で止まって確認することを名指しする
- ロールバック方法（Time Travel・ゼロコピークローンでの退避など、使う手段）か、実行前の確認手順（対象件数の事前確認、開発環境での先行実行）を書く。手段の可否を確かめていなければ「未確認」と書く

理由: データの上書きは git のように戻せない。実装者は完了条件に向けて進むので、止まる地点が書かれていなければ本番に対して実行する

## 現状と決定事項に書く論点

該当するものだけを書く。全部を節として並べない。

- 再実行・バックフィルしたとき結果が同じになるか（冪等性）と、その前提（MERGE のキー、パーティションの単位）
- スキーマ変更が下流（dbt の下流モデル・ダッシュボード・外部の参照）に与える影響
- ウェアハウスのサイズ・実行頻度など、コストが変わる選択
- 機微データの列と、権限（ロール・マスキング）の扱い
- 鮮度の要件と監視（遅延したときに誰がどう気づくか）

機能の可否（GA か Preview か、dbt Projects on Snowflake で使えるか）が決定の前提になるなら、確かめた出典と日付を「現状」に書く。確かめていなければ「未確認」と書き、確かめることを完了条件か停止条件に含める。

- 理由: これらは実装の途中で気づくと作り直しになる。現状に事実として、決定事項に選択として書けば、実装者は前提を取り違えない
