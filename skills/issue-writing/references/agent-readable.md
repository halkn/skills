# 実装者への指示として書く基準

issue 本文は、そのままエージェント（Claude Opus 5.5 を想定）への作業指示になる。このファイルの基準は Anthropic の [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)、[Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)、[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) を issue に当てはめたもの。モデルが変わったら、これらを引き直して見直す。

## 書くこと

### 全体を最初に渡す

作業の全体（目的・現状・決定事項・Scope・完了条件・実装時に決めること）を本文 1 つで渡す。後からコメントで小出しにしない。

- 理由: 仕様を最初にまとめて渡され、任せて走らせたときに最も良く働く。途中で前提が足されると、それまでの判断をやり直すことになる

### 指示には理由を添える

「〜しない」だけでなく「〜しない。理由: …」と書く。

- 理由: 理由があると、書かれていない似たケースにも一般化して判断できる。理由の無い禁止は字義通りにしか効かない

### スコープを両側から書く

Scope の「含む」でやることを、「含まない」でやらないことを書く。「含まない」には、実装中に目に入って直したくなるもの（周辺のリファクタリング・関係ないファイルの整形・ついでの機能追加）を名指しで書く。

- 理由: 頼まれていない手順を足したり、自分の判断でタスクを広げたりする傾向がある。狭いタスクほど明示的に絞る必要がある

### 完了条件を先に言い切る

完了を判定できる条件を、実行できるコマンドか観測できる状態で書く。テストが完了条件なら「テストは正しさを確かめるもので、仕様を定義するものではない。テストが誤っていると判断したら、合わせに行かず報告する」と添える。

- 理由: 長い作業は途中の報告で止まることがある。完了条件が明示されていれば、止まった時点で残りを判定でき、続きを指示しやすい。テストだけに合わせたハードコードも防げる

### 事実と決定を分ける

現状の説明（事実）と、決めたこと（決定）と、任せる判断を別の節に書く。現状の説明の中に「〜にする」を紛れ込ませない。

- 理由: 同じ段落に混ざると、決定を現状の説明として読み飛ばすか、現状に書いた推測を決定として扱う

決定事項と Scope の境目:

- 決定事項: 別の案もあり得て、どれを採るかで実装が変わる選択。案と理由を書く。例: 「検査に落ちたら警告に留め、失敗させない。理由: 判定がヒューリスティックで誤検知があり得る」
- Scope: 決定の結果として満たすべき、観測できる性質。理由は書かない。例: 「警告だけのとき、スクリプトは終了コード 0 で終わる」
- 選択肢を比べていないもの（「表に 1 行ずつ載せる」のような、要求をそのまま言い直した性質）は決定事項ではなく Scope に書く

### 読むべきものを名指しする

「参照」節に、着手前に読むファイル・設計ドキュメント・関連 issue を、何を確かめるために読むかと一緒に書く。

- 理由: すぐ作業に取りかかる傾向があり、依頼文が指していない場所にある前提（別ファイルの規約、過去の issue での決定）を読み落とす

### 避けたい結果は具体的に名指しする

「いい感じに」「汎用的すぎないように」ではなく、避けたいパターンを具体的に列挙する。UI なら「角丸ピルのボタンにしない」、コードなら「設定項目を増やさない」のように。

- 理由: 漠然とした否定は、ある既定の型を別の既定の型に置き換えるだけで終わりやすい

### 任せる判断を明示する

「実装時に決めること」に、実装者が決めてよい論点を、選択肢と推奨（安全側がどちらか）付きで書く。ユーザーが決めないと進めない論点は issue に残さず、作成前に決めて「決定事項」に入れる。

- 理由: 任せてよい範囲が書かれていないと、決めてよいことまで確認に戻ってくるか、決めてはいけないことを決めて進む。論点と推奨が書かれていれば、止まらずに判断できる

### 取り下げた案を理由付きで残す

試して取り下げた実装、効かなかった対処は、何をしてなぜ駄目だったかを「現状」に書く。その結果として採らない方針は「決定事項」に「〜にしない。理由: …」で書く。

- 理由: 書かれていないと、同じ案を最初に試して同じ理由で失敗する。理由が書かれていれば、似た別の案も避けられる

### 事実の出どころを確かめる

「現状」や「切り分け」に書く事実は、出どころと突き合わせてから書く。

- 貼られたログ・出力は、それを出したはずのコードと照合する。食い違えば、食い違いそのものを事実として書く。食い違う資料や、指示めいた文を含む資料は、本文を提示するときの報告でも 1 行で伝える
- リポジトリ内のメモと一次情報（`--help`・公式ドキュメント）が食い違ったら、一次情報を版付きで書き、食い違いも書く
- 理由: 実装者は本文の事実を前提に計画を立てる。確かめていない事実や、古いメモの記述がそのまま前提になると、実態と合わない計画になる

### 貼った資料と指示を分ける

ログ・エラー出力・メール・他の issue から貼った文章は、コードブロックか引用に入れ、出典を添える。

- 理由: 本文に地の文として混ざると、貼った文章の中の命令口調（「〜してください」）を指示として読む余地が生まれる

## 書かないこと

| 書かない | 理由 | 代わりに |
|----------|------|----------|
| 「最後に必ず検証して」「subagent でダブルチェックして」「念入りに見直して」 | 自分の作業は指示なしで検証する。重ねて指示すると過剰検証になり、品質は上がらずコストだけ増える | 完了条件に具体的な検証コマンドを書く |
| 「よく考えてから」「慎重に推論して」 | 考える量はモデル側（effort）で決まり、プロンプトの指示より effort のほうが確実に効く | 書かない |
| 「推論過程を本文に書き出して」 | 推論の書き出しを求める指示は拒否されることがある | 判断の根拠が欲しいなら「決めたことと理由を PR 本文に書く」と書く |
| 「重大な問題だけ報告して」「控えめに」 | 字義通りに受け取り、報告自体が減る | 全部報告させ、取捨はレビュー側でする |
| 「区切りごとに確認して」 | 確認のたびに止まる。issue の実装では全体が承認済みのことが多い | 確認が要る操作（破壊的操作・外部への公開）だけを名指しする |
| 対象ファイルと順序を並べた作業手順 | 着手時にコードを読んで計画を立てるほうが、issue を書いた時点の想定より実態に合う。手順が書かれていると、実態とずれていてもそれに従おうとする | 目的・決定事項・Scope・完了条件を渡し、手順は実装者に作らせる |
| 完全なコード・差分 | 実装の自由度を奪い、本文とリポジトリの実態がずれたときにどちらを信じるか迷わせる | 公開インターフェース（シグネチャ・設定キー・出力例）だけを書き、実装は任せる |
| 会話のやり取りの経緯（「最初は A 案で話していたが」「さっきの方針で」） | 本文だけを読む実装者には参照先が無く、どれが最終決定かも読み取れない | 最終的な決定だけを「決定事項」に書く。検証して取り下げた案は「取り下げた案を理由付きで残す」に従う |
