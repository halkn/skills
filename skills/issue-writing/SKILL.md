# Issue の書き方

## 適用範囲

GitHub issue の本文を作る・清書する手順。読み手は 2 人いる。後で読み返す自分と、その issue を渡されて実装するエージェント。後者は会話の経緯を知らないまま issue 本文だけを頼りに作業するので、本文だけで作業が完結する情報を書く。

- 対象リポジトリに `.github/ISSUE_TEMPLATE/` があれば、その見出しと必須項目を優先する。この skill の書式は、テンプレートが無いときの既定と、テンプレートの各欄を埋めるときの粒度の基準として使う
- 「issue を立てて」と依頼されたら作成まで行う。「この issue を書き直して」のように既存の issue の更新を依頼されたら、更新まで行う。「本文を書いて」「整えて」のように作成・更新を含まない依頼では、本文を提示して止める
  - 理由: issue の作成は他者に見える操作。依頼の範囲を超えて公開しない

## 種類を決める

最初に種類を決める。実装計画を基本の型とし、他の種類は基本の型の一部の節を置き換える。書式は [references/template.md](references/template.md) にある。

| 種類 | 使うとき | 基本の型との違い |
|------|----------|------------------|
| 実装計画 | 作るもの・変えるものがある。既定 | 基本の型: 目的 / 現状 / 決定事項 / Scope / 完了条件 / 実装時に決めること / 参照 |
| 小さな修正 | 決定事項が 1 つも要らない | 目的・Scope・完了条件だけを残す |
| 不具合 | 期待と違う挙動を直す | 「現状」を「事象 / 切り分け / 原因」に分ける |
| 検討 | 何をやるかがまだ決まっていない。結論を出すこと自体が作業 | 「決定事項」を「選択肢」に、「完了条件」を「判断基準」に置き換える |

迷ったら実装計画にする。検討の結論が出たら、実装は新しい issue に分ける。

## 粒度

1 issue = 1 PR でマージできる単位にする。

- 本文の中で「PR 1」「PR 2」と段階を分けたくなったら、issue を分ける。分けた issue 同士は「参照」で番号を示し合い、分けた理由を 1〜2 文で書く
- 同じ完了条件で確かめられる付随作業（README の表の更新、設計ドキュメントへの追記）は別 issue にせず、完了条件に含める
- 本文が長くなるのは「現状」と「決定事項」が厚いときであるべきで、Scope や完了条件が長いときは、1 つの PR に収まらない兆候であることが多い

## 手順

1. **材料を集める** — 会話で決まったこと、関連するコード・設計ドキュメント・既存 issue を読む。読み取りだけの確認（重複確認など）は、作成を含まない依頼でも行う。重複確認は `gh issue list --search "<キーワード>" --state all`。本文に書く事実は次のように確かめる
   - ファイルパス・関数名・コマンドは、実在を確かめたものだけを書く。「現状」は既定ブランチの状態を基準にする。作業ツリーで見た事実は `git show <既定ブランチ>:<path>` や `git ls-tree <既定ブランチ>` で確かめ直してから書き、未マージの変更に依存するならそう書く
   - 貼られたログ・出力や、リポジトリ内のメモを事実として使うときは、[references/agent-readable.md](references/agent-readable.md) の「事実の出どころを確かめる」に従う
   - ユーザーしか知らない事実（不具合の再現環境など）が欠けていても、作成を止めない。欠けている事実を本文に「未確認」として書き、報告で挙げる
1. **判断を分ける** — 書き始める前に、論点を次の 3 つに振り分ける。決定事項と Scope の境目は [references/agent-readable.md](references/agent-readable.md) の「事実と決定を分ける」にある
   - **ユーザーに聞く**: 答えによってデータモデルや外から見える振る舞い（公開インターフェース・出力・CI の成否・UX）が変わり、会話・既存の決定・リポジトリの規約のどれからも導けない論点。答えで設計が大きく変わるものから 1 問ずつ聞き、答えを「決定事項」に入れる
   - **自分で決める**: 既存の決定・規約から導ける論点。同じ仕組み（同じ CI、同じスクリプト群）の中で既に揃っている形式も規約とみなす。「決定事項」に書き、理由に導いた根拠（どの決定・どの規約か）を書く。このうち外から見える振る舞いに関わるものは、本文を提示するときの報告で 1 行ずつ挙げる
   - **実装者に任せる**: 外から見える振る舞いを変えない内部の選択（アルゴリズム・内部構造・ツールの選び方）。「実装時に決めること」に推奨付きで書く
1. **書く** — [references/template.md](references/template.md) の書式で書く。各節の中身は [references/agent-readable.md](references/agent-readable.md) の基準に従う
1. **見直す** — 下の「見直し」を 1 項目ずつ当てる
1. **作成・更新する**（依頼されたときだけ）— 本文をファイルに書き、新規なら `gh issue create --title "<title>" --body-file <file>` で作る。既存の issue の書き直しなら、`gh issue view <番号> --json title,body` で今の本文を読んでから書き直し、`gh issue edit <番号> --body-file <file>` で更新する。ラベル・assignee は依頼されたときだけ付ける。終わったら issue の URL を報告する
   - カレントディレクトリと別のリポジトリが対象なら、`gh` の各コマンドに `--repo <owner>/<repo>` を付ける。重複確認の `gh issue list` も同じ
   - 本文ファイルは、シェルの heredoc ではなくファイル書き込みツールで、作業ディレクトリの中の gitignore された場所（例: `.scratch/`）に書き、作業ディレクトリからの相対パスで渡す。作業ディレクトリの外へは書き込みに確認が要る環境があり、`$TMPDIR` などの環境変数は sandbox の内と外で展開先が変わって、書いたものと別のファイルを `gh` が読むことがある
   - git リポジトリの中なら、`gh` はリポジトリのルートで実行する。ignore されているかは `git check-ignore -q <path>` の終了コード（0 なら ignore 済み）で判定し（`-v` は `!` の否定パターンにも 0 を返す）、ignore された場所が無ければ置き場所を `git rev-parse --git-path info/exclude` が示すファイルに足してから使う。git リポジトリの外なら、この確認は要らない
   - 同じ置き場所を使う別セッションと衝突しないよう、ファイル名に issue の要旨と日時（`date +%Y%m%d%H%M%S`）を入れ、同名のファイルがあれば上書きせず別名にする
   - 互いに参照する issue を複数作るときは、参照される側から作り、得た番号を後の issue の本文に書く。先に作った issue への逆向きの参照は `gh issue edit <番号> --body-file <file>` で足す

## タイトル

- 実装計画・小さな修正は、完了したときの状態を動詞で終わる 1 文で書く。例: 「review-report の出力先を XDG state dir に移す」
- 不具合は、起きている事象を書く。例: 「smoke test が terminal チェック後に SIGSEGV で落ちる」
- 検討は、決めることを「〜か検討する」で書く。例: 「skill の版をタグで固定するか検討する」
- 「〜について」「〜の件」「〜の改善」のように、何をすれば終わりかが読めない名詞止めにしない

## 見直し

書き終えたら、次を 1 つずつ確かめる。当てはまらない節は削る（空の見出しを残さない）。

- 会話を知らない人が本文だけで着手できるか。「さっきの方針で」「例の件」のような、会話への参照が残っていないか
- 「現状」が、ファイルパス・コマンド出力で示されているか。既にあって使えるものと、足りないものが分かれているか
- 事実（現状）と決定（決定事項）と任せる判断（実装時に決めること）が、それぞれの節に分かれているか。現状や Scope の中に決定が紛れていないか
- 「決定事項」の先頭に、後から変わりやすい決定（データモデル・型・公開インターフェース・UX）が来ているか。各決定に理由があるか
- Scope の「含む」が実装手順ではなく、満たすべき性質になっているか。「含まない」に、やりたくなるが今回やらないことが書かれているか
- 完了条件が、実行できるコマンドか観測できる状態で書かれているか。「確認できる」「整理されている」「適切に動く」のような判定できない語が無いか。壊していないことの条件も入っているか
- 「実装時に決めること」に、ユーザーが決めないと進めない論点が残っていないか
- [references/agent-readable.md](references/agent-readable.md) の「書かないこと」に当たる指示が混ざっていないか
