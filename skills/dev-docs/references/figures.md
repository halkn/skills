# 開発の図

設計書・ADR・Runbook・README に入れる図の選び方と描き方。図は Markdown の中に Mermaid で書く。

figure-docs（<https://github.com/u-ichi/agent-plugins> の `plugins/figure-docs`）の開発の図の分類・ルール・見本を参考に、Markdown の開発文書に合わせて作った。

## 図にするか

- **図にする**：3つ以上の部品や関係者の関係、分岐のある流れ、状態の移り変わり、変更の前後。
- **表にする**：行と列の欄に文章が入る対応（部品と関心事の対応、案と観点の比較）は Markdown の表にする。
- **文章で書く**：2つのものの関係、分岐のない手順（Runbook・README では番号付きの箇条書き）、単独の数値。

## 図の形を選ぶ

1. **問いと言いたいことを1文に決める**：読み手がその図で何を判断するかを決め、言いたいことを1文にする（例：「決済の失敗は API と外部決済サービスの間で起きる」）。1枚の図で答える問いは1つにする。
2. **分類を決める**：その1文が何を見せるかを、下の分類から選ぶ。
3. **形を選ぶ**：分類の中から、下の「図の一覧」で形を選ぶ。一覧は目安で、言いたいことに合わなければほかの形でよい。
4. **置き場所で描けるかを確かめる**：ADO Wiki では一部の種類を描き替える（[platforms.md](platforms.md) の「表示できる図の種類」）。
5. **図の下に要点を1行書く**：図から読み取れることだけを書く。図から読み取れない主張は、図に足すか要点から外す。

## 分類

| 分類 | 見せること |
|---|---|
| 構造 | 何がどの部品でできていて、境界と依存の向きはどうか |
| やりとり | 誰が誰に、どの順で、何を頼み、何が返るか |
| 状態と手順 | 状態がどう変わり、処理がどこで分かれるか |
| データ | 何がどこに入り、どう流れ、どう関係するか |
| 配置 | どこで動き、どの境界をまたいで通信するか |
| 時間 | いつ何が起き、どの順で進むか |
| 変更 | 前と後で何が変わり、どの順で移すか |
| 性能と信頼性 | どこで時間や資源を使い、どれだけ失敗してよいか |
| 判断 | 案をどの観点で比べ、何を選ぶか |

## 開発の図のルール

- **1枚の四角は6つまで**：超えるときは範囲を分けた図にするか、連作にする。詰め込むと、読み手がどこを見ればよいか分からなくなる。
- **孤立した四角を描かない**：どの四角も、ほかの四角と矢印か `subgraph` の入れ子でつなぐ。
- **矢印に内容と同期・非同期を示す**：矢印には渡すもの（呼び出し、データ名、通信方式など）を書く。同期呼び出しは実線（`-->`）、応答や非同期は点線（`-.->`）にする。
- **段階が増える構成は連作にする**：部品が3つ以上増える構成や3段階以上の移行は、同じ配置の図を段階ごとに並べ、各段階で1つずつ足す。
- **変更の前後は同じ配置で色分けする**：前と後で同じ配置の図を並べ、追加するものを緑、削除するものを赤の点線、変更するものを太線にする（`classDef` と `linkStyle`）。変わらない箇所には印を付けない。
- **状態の図は先に一覧で検証する**：状態と遷移（出来事と条件）を一覧に書き出し、抜けと行き止まりを確かめてから描く。

## 言葉のそろえ方

- **用語をそろえる**：読み手が使っている名称に合わせ、同じものを図と文章で別の名前で呼ばない。
- **記号や略称はその図の中で説明する**：「案 A」のような作業中に付けた記号を図に出すときは、何を指すかを同じ図の中に書く。
- **元の文脈なしで通じる表記にする**：見出しや図中の要素名は、会話も元の資料も知らない読み手が、その文字と上の見出しだけで何を指すか分かる言葉にする。値には何の値かを添える（例：「要る時：11月末」ではなく「承認が必要な時期：11月末」）。
- **ほかの資料から見出しを借りるときも書き直す**：元の文脈を外して単独で読めるかを確かめ、要素名と値だけに縮まって意味が通じない見出しは書き直す。
