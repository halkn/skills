# ADR（Architecture Decision Record）

1つの判断と、その時に比べた案・理由を残す文書。読み手は、後で「なぜこうなっているか」を調べる人と、判断を覆すかを考える人である。1つの ADR に判断は1つだけ書く。

## 見出し

- 文書の題は、決めたことの1文にする（`# 0007. 認証は API Gateway でまとめて行う`）。番号は置き場所の既存の ADR に続ける。
- 節の見出しは「役割の名前：その節の結論の1文」にする（`## 決定：認証は API Gateway でまとめて行う`、`## 案 B を採らない：運用する人が足りない`）。役割の名前で ADR の型として拾い読みでき、結論で中身が分かる。
- 「状態」の節だけは値なので、結論の文にせず `## 状態：採用` のように値を書く。

## 型

```markdown
# NNNN. <決めたことの1文>

## 状態：<提案 / 採用 / 廃止 / NNNN で置き換え>

<決めた日>

## 状況：<判断が要った理由の1文>

<何が問題で、どの制約があったか>

## 決定：<決めたことの1文>

<何をどう決めたか。範囲と例外>

## 案 X を採らない：<理由の1文>

<比べた案ごとに1節。案が3つ以上か、観点が3つ以上なら、節を分けずに設計案の比較表を1つ置く>

## 結果：<この判断で起きることの1文>

<良くなること、悪くなること、後で見直す条件>
```

## 図

- 図は補助で、案の比較が要るときだけ入れる。案ごとの構成の違いを見せるなら「変更の前と後」と同じく同じ配置で並べ、観点で比べるなら設計案の比較表（Markdown の表）にする。
- 1つの案の説明だけなら図を入れない。

## 書かないこと

- 判断の後の作業計画。issue か設計書に分ける。
- 採用済みの ADR の書き換え。判断を変えるときは新しい ADR を書き、古い方の状態を「NNNN で置き換え」にする。
