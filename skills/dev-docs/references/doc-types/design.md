# 設計書

何をどう作るか、なぜその構成にしたかを残す文書。読み手は、実装する人・レビューする人・後で変更する人で、判断の根拠を探しに来る。

## 見出し

- 節の見出しは、その節の結論を1文で書く（「認証は API Gateway でまとめて行う」）。「認証」のような題名だけの見出しにしない。読み手は見出しを拾い読みして、どの判断がどこに書いてあるかを探す。
- 文書の題は「<対象>の設計」のような名前でよい。
- 「決めていないこと」「参照」のような役割の節は、結論の文にせず役割の名前のままにする。

## 型

```markdown
# <対象>の設計

<何を作るか、何を決めたかを3行以内で。読み手がこの文書を読むべきかをここで判断できるようにする>

## <構成についての結論の1文>

<構成の図（System Context か Container diagram）と、要点1行>

## <やりとりについての結論の1文>

<Sequence diagram と、要点1行。失敗したときの動きを含める>

## <状態かデータについての結論の1文>

<State machine・ER diagram・Data flow diagram のうち要るもの>

## <採らなかった構成についての結論の1文>

<比べた案と、採らなかった理由。比べる観点が3つ以上なら設計案の比較表>

## 決めていないこと

<未定の点と、決める人・決める時期。無ければ節ごと書かない>

## 参照
```

- 節は型の順でなくてよく、要らない節は書かない。構成の節は省かない。
- 構成の図を最初の節に必ず1枚入れる。やりとり・状態・データの節も、図を中心にして文章は要点と補足に絞る。
- 長い根拠や計算は本文から外す。GitHub では `<details>` に折りたたみ、ADO Wiki では子ページに分けてリンクする（ADO の docs は `<details>` を挙げていない）。

## 書かないこと

- 作業の手順や運用の手順。Runbook に分けてリンクする。
- 経緯（いつ誰が何を言ったか）。決まったことと理由だけを書く。
