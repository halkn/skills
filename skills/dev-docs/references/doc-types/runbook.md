# Runbook

運用の作業や障害の対応を、作業しながら引いて読む文書。読み手は作業中の当番で、急いでいることが多い。目次から自分の状況の節を探し、手順を上から1つずつ実行する。

## 見出し

- 節の見出しは項目名にする（「前提」「再起動する」「切り戻す」）。結論の文にしない。読み手は目次から状況に合う項目を探すため、結論の文では探せない。
- 症状から引く Runbook は、症状を見出しにする（「API が 503 を返す」）。読み手はアラートやログの文字で探す。
- 手順の節の見出しは動詞で終える（「キャッシュを消す」）。

## 型

```markdown
# <対象>の<作業>

<この Runbook を使う場面を1〜2文で。使わない場面があれば書く>

## 前提

- <要る権限・ツール・接続先>

## <手順の項目名>

1. <1手順1動作。実行するコマンドはコードブロックで、そのまま貼れる形にする>
2. <結果の確かめ方と、期待する出力>

## 確かめる

<作業が済んだと判断する条件>

## 切り戻す

1. <元に戻す手順>

## 連絡先

<手順で直らないときに連絡する先と、伝えること>
```

## 手順の書き方

- 手順は番号付きの箇条書きにし、1つの番号に動作を1つだけ書く。
- コマンドは置き換える値を `<…>` で示し、どこから値を取るかを直前に書く。
- 結果を見て分かれる所（「503 が続くなら手順 5 へ」）は手順の中に書く。分かれが3つ以上あるときだけ、判断の流れを Flowchart で描く。
- 危険な操作（削除・本番の再起動）の前には、取り返しが付くかと確かめることを書く。

## 図

- 図は補助で、判断の分かれと、作業の流れが3段階以上で順を見失いやすいときだけ入れる。
- 図の中の手順と本文の手順の番号をそろえる。

## 書かないこと

- 設計の理由。設計書へのリンクにする。
- 「〜しましょう」「〜すると良いでしょう」。手順は「〜する」で書く。
