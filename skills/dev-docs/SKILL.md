# dev-docs

人が読むリポジトリの文書を、拾い読みできる形で書く。dev-docs が決めるのは文書の種類・型・見出し・図の比重までで、図の描き方は [references/figures.md](references/figures.md)（figure-docs を参考にした開発の図の決まり）に、文の推敲は yomiyasu に任せる。文体は「である調」にする。

## 使わない依頼

| 依頼 | 使うもの |
|---|---|
| Claude Code・エージェントに実装を依頼する issue・設計書、別のセッションへの引き継ぎ | handoff |
| PR の本文、commit message | git-flow |
| 上司や事業部に見せる HTML・スライドの説明資料 | figure-docs など、その資料の skill |
| 「yomiyasu で推敲して」のような推敲だけの依頼 | yomiyasu |

設計書の依頼が「人が読んで判断する文書」か「エージェントに渡す実装計画」か決まらないときは、読み手を1行で確かめる。答えを待つ間に、種類と置き場所の判定まで進めてよい。

## 1. 文書の種類を決める

| 種類 | 選ぶとき | 見出し | 図の比重 | 型 |
|---|---|---|---|---|
| 設計書 | 何をどう作るか、なぜその構成かを残す | 節の結論を1文で | 図が中心（構成・やりとり・状態・データ） | [design.md](references/doc-types/design.md) |
| ADR | 1つの判断と、比べた案・理由を残す | 節の結論を1文で | 補助（案の比較が要るときだけ） | [adr.md](references/doc-types/adr.md) |
| Runbook | 運用の作業や障害の対応を、作業しながら引いて読む | 項目名 | 補助（判断の分かれ・流れだけ） | [runbook.md](references/doc-types/runbook.md) |
| README | リポジトリやフォルダの入口 | 項目名 | 補助 | [readme.md](references/doc-types/readme.md) |

- 依頼に種類の名前（設計書・ADR・Runbook・手順書・README）があればそれに従う。手順書・運用手順書は Runbook として扱う。
- 名前が無ければ、読み手がその文書を開く場面で決める。判断の根拠を探す → 設計書、1つの判断の理由を探す → ADR、作業中に手順を引く → Runbook、初めて来て使い始める → README。
- 1つの文書に種類は1つにする。設計書に運用の手順が入るなら、手順は Runbook に分けてリンクする。
- 既存の文書の書き直しでは、元の種類と置き場所を保つ。種類が合っていないと判断したら、書き直す前に分け方を報告する。

完了条件: 種類が1つに決まり、型のファイルを読んでいる。

## 2. 置き場所を決める

置き場所は Azure DevOps Wiki か GitHub。Mermaid はどちらも ```` ```mermaid ```` のコードブロックで書き、置き場所で変わるのは表示できる図の種類（ADO Wiki は `graph` で書き、C4 系などは使えない）と目次・ファイル名の決まりである。決め方と記法は [references/platforms.md](references/platforms.md) にある。

## 3. 書く

1. **材料を集める**：会話・コード・設定・既存の文書から事実を集める。コードから分かる値（ポート、コマンド、パス、設定の名前）は推測で書かず、ファイルで確かめる。確かめられない値は本文で断定せず、「未確認」と書いて報告に挙げる。
2. **見出しを先に全部書く**：型に沿って、見出しだけの骨組みを作る。見出しは表の「見出し」の列と型のファイル、下の「見出しの方針」に従う。骨組みだけで、読み手が要る節を探せるかを確かめる。
3. **図を入れる**：表の「図の比重」の列と型のファイルが挙げる場面に、[references/figures.md](references/figures.md) を読んで図を選び、Mermaid で書く。
4. **本文を書く**：「である調」で、型のファイルの書き方に従って書く。経緯は書かず、決まったことと理由を書く。
5. **推敲する**：下の「yomiyasu で推敲する」に従う。
6. **確かめる**：下の「出す前に確かめる」を上から確かめる。

既存の文書を更新するときは、同じ話題の節を書き換える。節を足すのは新しい話題のときだけにする。追記を重ねると、読み手が最新の内容を探せなくなる。

## 見出しの方針

種類ごとの形（設計書・ADR は節の結論の1文、Runbook・README は項目名）とその理由は、型のファイルの「見出し」にある。どの種類にも次を当てる。

- **役割の節は名前のままにする**：「決めていないこと」「参照」「前提」は、どの種類でも結論の文にしない。
- 見出しの中の短い文字も、会話を知らない読み手に通じる言葉にする（[references/figures.md](references/figures.md) の「言葉のそろえ方」）。

## yomiyasu で推敲する

yomiyasu は、名前を出して頼まれたときだけ動く推敲の skill である。dev-docs の手順から名前で呼ぶ。dev-docs には同梱しない。入れ方は <https://github.com/nanaism/yomiyasu> の README にある。

### 入っているかを確かめる

その時点の skill の一覧に `yomiyasu`（プラグインで入れたときは `yomiyasu:yomiyasu`）があるかを見る。

- 無いとき：推敲を飛ばして次の手順に進み、作業は止めない。報告に「yomiyasu が入っていないため推敲を飛ばした」と書き、上の入れ方の場所を添える。
- あるとき：下の依頼文で呼ぶ。

### 呼び方

Skill ツールで yomiyasu を呼び、依頼文に次を入れる。種類ごとの見出しの方針は「指定された見出しの形」として渡す。yomiyasu は依頼で指定された見出しの形を直さないが、指定が無いと見出しを短い項目名に直すため、設計書・ADR の結論の1文の見出しが崩れる。

```text
yomiyasu で <文書のパス> を推敲し、原文のファイルを更新してください。
- 文書: <種類>（<置き場所>）に置く、開発者が読む技術文書
- 種類: manual
- 文体: である調
- 見出し: 見出しは指定された見出しの形です。<種類ごとの方針>なので、見出しの文言と数と順を変えないでください。
- Mermaid のブロック、コードブロック、コマンド、表の値、識別子は変えないでください。
```

`<種類ごとの方針>` には、設計書・ADR なら「節の結論を1文で書く形」、Runbook・README なら「目次として拾い読みされる項目名」と書く。「種類: manual」の行は Runbook・README のときだけ入れ、設計書・ADR では行ごと消す。設計書・ADR に種類を渡さないのは、yomiyasu の種類（manual・formal・proposal など）のどれにも当たらず、当たらない種類を渡すと、その種類で当てない規則が外れるためである。

### 推敲のあと

- yomiyasu が原文とは別の名前で保存した最終稿や抜き書き（`*.material.txt`）が文書の置き場所に残っていれば、原文に写されたことを確かめてから消す。`.yomiyasu/` は yomiyasu が自分で git の対象から外す。
- yomiyasu が返した「書き手に確かめたい点」は、利用者への報告に含める。
- 推敲で見出し・Mermaid・コマンドが変わっていたら、元に戻す。

## 出す前に確かめる

- [ ] 種類が1つで、型のファイルの節の順と書かないことに従っている
- [ ] 見出しが種類ごとの方針どおり（設計書・ADR は結論の1文、Runbook・README は項目名）
- [ ] 図の比重が種類どおり。設計書には構成の図がある。ADR・Runbook・README に要らない図を足していない
- [ ] Mermaid が ```` ```mermaid ```` で書かれ、図の種類が置き場所に合っている（ADO Wiki は `graph`）
- [ ] 図の矢印に渡すものが書いてあり、四角が1枚に6つまで
- [ ] 本文が「である調」で、Runbook・README の手順が番号付きの箇条書き
- [ ] 確かめていない値を断定で書いていない
- [ ] 推敲を実行したか、飛ばした理由を報告に書く
- [ ] yomiyasu の別名の最終稿・抜き書きが置き場所に残っていない
- [ ] ADO Wiki に新しいページを足したら `.order` にも足した

## 報告

次を短く書く。

- 書いた・直した文書のパス
- 種類と置き場所の判定（依頼から決めたか、推定したか）
- 推敲：yomiyasu で実行したか、飛ばしたか（理由）
- 未確認の値と、yomiyasu の「書き手に確かめたい点」
