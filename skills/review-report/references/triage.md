# 仕分けの基準

`/code-review` の指摘に `severity` と `disposition` を付け、issue の完了条件と diff を照らすときの基準。コードの観点（何を指摘するか）はここに書かない。それは `/code-review` が持つ。

## severity

レビューが severity を出していればそのまま移す。出していない場合だけ、`failure_scenario` の実害から決める。

- `HIGH` — データの破壊・情報漏洩・不可逆な操作、または本番の主要な経路が壊れる
- `MEDIUM` — 実際に踏む条件があり、踏むと誤った出力になる
- `LOW` — 実害はあるが条件が限定的、または品質・保守性の問題

## disposition

マージ可否は `disposition` と要件の対応表から決まる。`fix-now` が 1 件でもあれば「このままはマージしない」、それが無くても `ask` か満たすと言えない要件があれば「確認待ち」になる。その重みで判断する。

- `fix-now` — 今回の変更が持ち込んだ欠陥で、マージ前に直すもの
- `ask` — 意図や仕様が diff と issue から断定できず、ユーザーに確かめないと仕分けられないもの
- `issue` — 実害はあるが、今回の変更に起因しない（既存バグ）か、修正が今回の範囲を超えて別 PR になるもの
- `wont-fix` — 意図した挙動、実害が無視できる、または今回の設計判断として受け入れるもの

`issue`・`wont-fix` には `disposition_reason` に理由を 1 文で書く。`ask` には確かめたいことを 1 文で書く（無いと `render_review.py` が落とす）。

### fix-now にするかは、変更が作る契約で決める

その変更が作る契約の中に、壊れる入力があるかで決める。契約とは、変更が公開する関数・CLI の引数・設定のキー・環境変数・受け付けるファイルの形式のように、呼び出し側が渡せるものの範囲を指す。

- 「今の呼び出し元では踏まない」「固定値しか渡していない」は見送る理由にしない。変更が値を受け付けるようにしたのなら、受け付けた範囲で壊れるかを見る
- 壊れる入力で再現できたら、`failure_scenario` に再現したと書く。再現していないなら、そう書く
- 契約の外の入力（型や schema で拒否される値、ドキュメントで受け付けないと明記した値）で壊れるだけなら `fix-now` にしない

迷ったら `fix-now` に寄せない。`fix-now` は「マージを止める」という主張なので、止めるほどではないものは `issue` にする。

### ask は推測の代わりに使う

業務仕様・設計の意図・issue に書かれていない前提に依存する指摘は、推測で `fix-now` や `wont-fix` に決めない。`ask` にして、ユーザーが答えれば仕分けが決まる問いを書く。

- 良い問い: 「空の入力で何も出さないのは意図どおりか（エラーにするなら `fix-now`）」
- 悪い問い: 「この実装で問題ないか」（答えても仕分けが決まらない）

コードを読めば決まることは `ask` にしない。周辺のコード・既存の類似実装・issue を読んでから、それでも決まらないものだけを `ask` にする。

## 要件との突合

issue の完了条件を 1 項目ずつ diff と照らし、`findings.json` の `requirements` に書く。`/code-review` は diff の正しさを見るが、issue に書かれたことが実装されているかは見ない。

### issue を見つける

次の順に探し、最初に見つかったものを使う。

1. PR モードなら PR 本文の `Closes #<n>` / `Fixes #<n>` / `Resolves #<n>`
2. ブランチ名に含まれる issue 番号（`fix/42-...` など）
3. ブランチのコミットメッセージの `#<n>`

見つかったら本文を取る。`gh` は単体で実行する。

```bash
gh issue view <n> --json body --jq .body
```

見つからない、`github.com` 以外のホスト、複数の issue に当たって 1 つに決められないときは、突合をせず、しなかった理由を報告に書く。issue を推測で選ばない。

### 照らし方

`## 完了条件` の節（handoff skill の issue の形式）があればその項目を、無ければ本文の箇条書きのうち実装の結果として確かめられるものを 1 項目ずつ取る。

- `met` — diff で満たしている。`evidence` に `path:line` を書く
- `missing` — 要件にあるのに diff に無い
- `unclear` — 満たしているか diff だけでは決まらない（手での確認が要る・別の PR でやる約束かもしれない、など）

`missing` を指摘として `findings` に重ねて入れない。diff に位置が無いので「diff 外」になるうえ、同じ欠落が 2 回数えられる。

逆向き（diff にあって要件に無い変更）は `requirements` に入れない。範囲外の変更が気になるなら、`/code-review` の指摘と同じく `findings` に `ask` で入れる。

## 人が仕分けを変えたとき

ユーザーが提示した仕分けを変えたら（「#3 は直さなくていい」「#5 は issue に」など）、そのとおりに直し、最後の報告に「#3 を `fix-now` から `wont-fix` に変えた（理由）」の形で 1 行残す。提示の前にユーザーが仕分けを指示したときは、この基準で付けたはずの仕分けを元の値として同じ形で残す（基準とユーザーの判断が一致していれば残さない）。同じ直しが続いたら、この文書の基準を直す材料になる。
