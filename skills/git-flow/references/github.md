# GitHub（`gh`）

`gh` 固有の手順。共通のフロー・コミット規約は `SKILL.md` を参照。

## PR テンプレート

PR を作る前に、リポジトリにテンプレートがあるか確認する。

```bash
git ls-files | grep -i pull_request_template
```

GitHub が認識する場所は、リポジトリルート・`.github/`・`docs/` に置かれた `pull_request_template.md`（大文字小文字は区別されない）。複数テンプレートを持つリポジトリでは `.github/PULL_REQUEST_TEMPLATE/` 配下に複数ファイルが並ぶ。その場合は変更内容に最も合うものを選び、判断が付かなければユーザーに聞く。

テンプレートは既定ブランチのものが使われる。作業ブランチでテンプレート自体を追加・変更している場合、作業ツリーの内容と実際に適用されるものが食い違うので、`git ls-tree -r --name-only origin/HEAD | grep -i pull_request_template` で既定ブランチ側を見る。

**`--body-file` / `--body` を指定すると、テンプレートは適用されない。** `gh` がテンプレートを自動で読み込むのは対話的なエディタ起動時だけで、本文を明示指定した時点で上書きされる。テンプレートの中身を読み、埋めたものを自分でファイルに書いて `--body-file` に渡す。

## PR 作成

```bash
gh pr create --title "<title>" --body-file <file> --base <branch>
```

- `--base` は省略するとリポジトリの既定ブランチ。既定ブランチ以外へ向けるときだけ明示する
- 本文はファイルに書いて `--body-file` で渡す。`--body` に長い文字列を渡すと改行やバッククォートのエスケープで壊れやすい。`--body "$(cat <<EOF ...)"` は使わない（`SKILL.md` の実行形の規則に反する）
- 本文ファイルは、リポジトリの外の、環境変数を含まない一意な絶対パスに置く（ブランチ名などを入れる）。ファイルを書く側にも `gh` にも、同じリテラルのパスを渡す
- 本文ファイルは、シェルの heredoc ではなく、ファイル書き込みツールで作る。本文にコマンド名が入っていると、heredoc を含む複合コマンドとして拒否する環境がある
  - 理由: `$TMPDIR` などの環境変数は、sandbox の内と外で展開先が変わる環境がある。そうなると書いたファイルとは別のファイルを `gh` が読み、古い本文のまま PR ができる。共有ディレクトリでは、名前が固定だと他のセッションの残骸と衝突する
- 途中段階なら `--draft`
- 作成後に `gh pr view <番号> --json body --jq .body` で読み返し、意図した本文になっているか確かめる
- 作成後に PR 番号・URL を報告する。`--web` でブラウザを開かない（ヘッドレス環境で止まる）

本文を渡す他の `gh` コマンド（`gh pr comment` / `gh issue create` / `gh pr edit`）にも同じ規則を適用する。

## issue の紐付け

PR 本文に `Closes #123` / `Fixes #123` と書くと、マージ時に issue が自動 close される。単に参照したいだけなら `#123` を裸で書く（close されない）。

commit メッセージ側にも `#123` は書けるが、PR 本文に書くほうが確実で、後から編集できる。

## マージ

```bash
gh pr checks <番号>
gh pr merge <番号> --merge
```

- マージ方式のフラグ（`--merge` / `--squash` / `--rebase`）は必ず明示する。省略すると対話プロンプトが出てこの環境では止まる
- `--admin` はブランチ保護を迂回する。ユーザーが明示的に指示した場合だけ使う
- `--delete-branch` は指示されたときだけ付ける
- 必須チェックが完了していない PR に `--auto` を付けると、条件が揃った時点での自動マージになる。即時マージのつもりで使わない

## その他

- レビューは `gh pr view <番号> --comments`
- issue 作成は `gh issue create`

## 確認プロンプトが出た場合

環境によっては `gh pr create` や `gh pr merge` に hook や permission 設定が掛かっており、対象リポジトリによって確認プロンプトが出る。これは想定された動作なので、フラグを変える・別コマンドで代替するといった回避を試みず、ユーザーの判断を待つ。
