# Git 作業手順

## 適用範囲

この skill は Git 操作の**手順**を扱う。ホスティング先は GitHub（`gh`）を前提とする。`gh` 固有の手順は `references/github.md` にある。

次のガードレールは手順の前提であり、skill の発火に関係なく常時適用される。ユーザーのグローバル設定（`~/.claude/CLAUDE.md` など）に同種の規定があれば、そちらが正。食い違ったらグローバル側に従う。

- コミット・push・PR 作成は、作業前に作成したブランチ上で行う
- push は自分の作業ブランチ（セッション開始時のブランチ、または自分が作成したブランチ）のみ。main/master へ直接 push しない
- 破壊的操作（`git reset --hard`、強制切替、ブランチ削除など）は事前に確認する
- 1 リポジトリに複数の worktree があり得る。他の worktree の作業を壊さないよう、`git worktree remove` / `git worktree prune` / worktree が使用中のブランチの削除は事前に確認する
- ユーザーの未コミット変更を戻さない

## コマンドの使い分け

- ブランチ切替は `git switch`、ファイル復元は `git restore` を使う。`git checkout` は使わない
  - 理由: `git checkout` は「ブランチ切替」と「ファイル破棄」という危険度の異なる 2 つの機能を 1 コマンドに持つ。引数を 1 つ間違えるだけで未コミット変更が消える。`switch` / `restore` は用途が分かれているため、その事故が構造的に起きない
- 対話的フラグ（`git rebase -i`、`git add -i` 等）はこの環境では動かない。非対話の等価な手段に置き換える
- PR・issue・CI の操作は `gh` を使う。ブラウザや Web UI の手順を案内しない

## 基本フロー

作業の開始前と終了時に `git status --short` を確認する。開始前の確認は「ユーザーの未コミット変更が既にあるか」を知るため、終了時の確認は「意図しないファイルを巻き込んでいないか」を知るためで、目的が違うので両方行う。

1. **ブランチを作成する** — 作業前に必ず作る。`git switch -c <branch>` で、main/master 上で直接作業を始めない
1. **実装する**
1. **差分を確認する** — `git status --short` と `git diff` を見て、意図した変更だけが含まれているか確かめる。ここで初めて気づく巻き込みは珍しくない
1. **コミットする** — 自分が変更したファイルだけを明示的に `git add` する。下記の粒度・メッセージ規約に従う
1. **push する** — 自分の作業ブランチへ
1. **PR を作成する** — `references/github.md` の手順に従う

PR 作成まで依頼された場合は、ブランチ作成から PR 作成までを途中確認なしで一気に実施してよい。ステップごとに許可を求めると、ユーザーは既に全体を承認しているのに何度も同じ判断を繰り返すことになる。

依頼されていない範囲には進まない。「コミットして」は commit までであり、push や PR は含まない。

## リモートの確認

この skill の PR・issue の手順は GitHub 前提なので、作業前にリモートを確認する。

```bash
git remote -v
```

`git remote get-url origin` でもよいが、`git remote -v` ならリモートが複数あるケースもまとめて見える。`origin` 以外に push する構成なら、その push 先の URL で判定する。

`github.com` 以外（Azure Repos・GitLab・社内の自前ホスティング）だった場合、PR 作成の CLI も issue の紐付け記法も違う。推測で `gh` を叩かず、ユーザーに確認する。誤ったホストの CLI は失敗するだけで済むが、記法を誤ったコミットは履歴に残る。

同一セッション内でも、リポジトリを跨いだら確認をやり直す。

## コミット対象の選び方

`git add .` と `git commit -a` を使わない。**自分が変更したファイルをパスで明示して `git add` する。**

作業開始時点でユーザーの未コミット変更が既にあることは珍しくなく、一括 add はそれを黙って巻き込む。ガードレールの「ユーザーの未コミット変更を戻さない」は破壊を防ぐが、巻き込みは防げない。巻き込まれた変更はユーザーの意図しないタイミングで履歴と PR に入り、しかも取り除くには結局手作業になる。

差分確認の `git status --short` で自分の変更以外が見えたら、それには触れない。コミット後に `git status --short` を再確認し、触れていない変更がそのまま残っていることを確かめる。

## 変更の粒度

1 つのコミットは 1 つの目的に絞る。無関係な整形・リファクタリング・タイポ修正を混ぜない。

これは美観の問題ではなく、後から `git revert` や `git bisect` で 1 コミットを単位として扱えるかどうかの問題。目的が 2 つ混ざったコミットは、片方だけを戻したくなった時点で手作業になる。

作業中に範囲外の改善点に気づいた場合は、混ぜずに別コミットへ分けるか、ユーザーに伝えて判断を仰ぐ。

## コミットメッセージ

小文字の conventional 形式の prefix + 短い英語要約。

```text
<prefix>: <summary>.
```

prefix は `fix:` / `add:` / `feat:` / `refactor:` / `docs:` / `chore:` などを使う。要約は 1 つのツール・1 つのテーマに絞る。

**例:**

```text
fix: python lsp settings.
add: fzf keybindings for git branch switch.
refactor: split nvim plugin specs by domain.
```

コミット対象のリポジトリに既存の履歴があるときは、`git log --oneline -20` で実際の書式を確認し、そちらに合わせる。ここに書いた規約はデフォルトであって、リポジトリ固有の慣習が優先される。

issue の参照記法は `references/github.md` に書いている。

## PR 本文の共通要件

**リポジトリに PR テンプレートがあれば、それが最優先**。テンプレートはそのリポジトリのレビュアーが「PR にこれを書いてほしい」と明示した合意なので、こちらの既定の書式より優先する。テンプレートの見出し・チェックリストの項目を勝手に削らず、構造を保ったまま埋める。埋められない項目は消さずに、理由を一言添えるか未チェックのまま残してレビュアーに判断を委ねる。

テンプレートの探し方と、CLI から渡す方法は `references/github.md` を見ること。

テンプレートが無い場合は、以下を書く。

- **変更理由** — 何を解決するのか
- **影響範囲** — どのコンポーネント・ディレクトリに及ぶか
- **確認手順** — 実行した検証コマンドと結果

テンプレートがある場合も、これらの内容がテンプレートの自由記述欄に収まるなら書く。テンプレートの項目と重複するなら繰り返さない。

見た目が変わる変更のときだけスクリーンショットを添える。

`~/.claude/plans/*.md` に計画ファイルがあれば、commit メッセージや PR 本文の下書き、受け入れ条件の元ネタとして使ってよい。

## マージ

マージは PR 作成の続きではない。「PR を作って」に続けて勝手にマージしない。明示的に依頼されたときだけ実行する。

1. **対象の PR を特定する** — 現在のブランチに対応する PR。複数該当するなら確認する
1. **CI の状態を確認する** — 失敗しているチェックがあればマージせず報告する。ブランチ保護で必須チェックが設定されていれば CLI 側も弾くが、弾かれない設定のリポジトリもある
1. **マージ方式を決める** — 既定は履歴を保持する通常の merge。squash / rebase はリポジトリの方針として指定されているときに使う
1. **マージする** — コマンドは `references/github.md` を見る

マージ方式はリポジトリ側の指定が優先される。対象リポジトリの CLAUDE.md / AGENTS.md、ブランチ保護設定、既存の履歴（`git log --oneline --merges -10` でマージコミットの有無を見る）のいずれかに方針が読み取れれば、そちらに従う。

ソースブランチの削除はマージと同時に指示されたときだけ行う。他の作業ツリーがそのブランチを使っている可能性があるため、既定では消さない。

## 変更を戻す・履歴を直す

「元に戻して」が指す対象は複数ある。どれなのかを確定してから実行する。取り違えると復旧できないものがある。

| やりたいこと | コマンド | 失うもの |
|---|---|---|
| 未コミットの変更を捨てる | `git restore <path>` | その変更（復元不可） |
| ステージだけ解除する | `git restore --staged <path>` | なし |
| push 済みのコミットを取り消す | `git revert <commit>` | なし（打ち消しコミットを積む） |
| 直前のコミットを書き直す | `git commit --amend` | 元のコミット（push 前に限る） |
| 未 push のコミットを取り消す | `git reset --soft HEAD~1` | コミットのみ（変更は作業ツリーに残る） |

- 対象パスは必ず明示する。`git restore .` はユーザーの未コミット変更を巻き込む
- 既に push したコミットは `git revert` で取り消す。履歴を書き換えないので、他の作業ツリーや共同作業者を壊さない
- `git reset --hard` と `git push --force` は事前確認が要る。force が避けられない場合も `--force-with-lease` を使い、リモートに他人の新しいコミットがあれば止まるようにする
- 何を消すか自信が持てないときは、先に `git stash` か作業ブランチのバックアップ（`git branch <name>-backup`）を取る

`git rebase -i` はこの環境では動かない。履歴の整理を頼まれたら、非対話でできる範囲（`--amend`、`git reset --soft` + 再コミット）に置き換えるか、対話が必要な旨を伝えてユーザーに実行してもらう。
